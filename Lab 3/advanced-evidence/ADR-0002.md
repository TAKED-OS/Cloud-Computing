# ADR-0002. PostgreSQL в приватной подсети

## Контекст

В исходной учебной конфигурации nginx, PHP и PostgreSQL работают на одном EC2. По заданию №3 приложение должно сохранить данные при переносе и подключаться к отдельной базе по приватному DNS-имени. Эксперимент проводится на новой VPC и синтетических данных.

## Решение

Разместить PostgreSQL 16 на отдельном EC2 в приватной подсети без публичного IPv4. Разрешить 5432 из группы безопасности приложения. Использовать приватную DNS-зону Route 53 с записью `db.timecapsule.internal`. Для администрирования подключаться через bastion.

## Рассмотренные альтернативы

| Вариант | Преимущество | Недостаток |
|---|---|---|
| PostgreSQL на EC2 приложения | Минимум компонентов и простое локальное подключение | Общее время простоя, конкуренция за CPU и память, сложнее масштабировать приложение |
| PostgreSQL на отдельном EC2 в публичной подсети | Независимый жизненный цикл, простой доступ к репозиториям пакетов | Требуется особенно аккуратно управлять маршрутизацией, адресами и входящими правилами |
| PostgreSQL на отдельном EC2 в приватной подсети | База изолирована от входящего интернета, приложение подключается по приватному имени | Для обновлений нужен временный исходящий маршрут и NAT |

## Последствия

База доступна приложению по DNS внутри VPC. Остановка и запуск EC2 сохраняют его приватный адрес, пока используется тот же сетевой интерфейс. При пересоздании сервера A-запись нужно сверить и при необходимости обновить.

На время обновления пакетов создаётся зональный NAT, привязанный к учебной публичной подсети. Тариф Frankfurt составляет 0,052 USD/ч и 0,052 USD/ГБ. Отдельно начисляется 0,005 USD/ч за его IPv4. После теста маршрут, NAT и его адрес удаляются в порядке, указанном в плане.

Elastic IP приложения даёт стабильный публичный адрес при остановках и запусках. Когда перед приложением появится ALB, пользователи будут обращаться по DNS балансировщика, и адрес отдельного узла перестанет быть точкой входа.
